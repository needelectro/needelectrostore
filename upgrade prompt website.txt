### 6. PRODUCT IMAGE MANAGEMENT — CRITICAL REQUIREMENT

Upgrade the existing ERP product creation and editing forms.

The administrator must be able to add product images in two ways:

**Method A — Device upload**
- Upload images from a computer or mobile device.
- Support appropriate formats such as JPEG, PNG, and WebP.
- Validate file type and size on the server.
- Generate optimized image variants where appropriate.
- Show upload progress, preview, and meaningful error messages.
- Allow the administrator to replace or remove images according to permissions.
- Support multiple product images if the current schema can accommodate them safely.

**Method B — External image URL**
- Provide a field for an image URL.
- Validate the URL and allow only approved HTTP/HTTPS image sources.
- Preview the image before saving.
- Handle unavailable or invalid images gracefully.
- Avoid server-side request forgery when validating remote resources.
- Never render untrusted URLs as executable content.

#### Image storage and delivery

Inspect the current storage implementation before selecting a solution.

Prefer the existing compatible storage provider if it is suitable. If the project uses Supabase Storage, inspect its current buckets, access policies, and upload configuration before modifying them.

Do not store large image files directly in database records.

Store image metadata and stable image references in the existing product schema or an appropriately reviewed migration.

Ensure that:

- Image records remain associated with the correct product.
- Product image ordering is predictable.
- Primary images are clearly defined.
- Storage access permissions are correct.
- Public product images can be delivered to customers.
- Private administrative assets remain protected.
- Deleted or replaced images do not break existing product records.
- Existing product images are preserved and migrated safely if needed.

#### Customer-side image display

Every eligible published product should display its primary image on:

- Homepage product cards.
- Category listings.
- Search results.
- Product detail pages.
- Cart and checkout summaries.
- Relevant order views.

Use responsive image sizing, appropriate compression, lazy loading below the fold, and prioritized loading for the main above-the-fold image.

Provide a consistent fallback image for genuinely unavailable images.

Do not silently hide product images when an image URL is temporarily unavailable.

### 10. CONNECT WEBSITE ORDERS TO THE EXISTING ERP

The existing ERP must remain the operational source of truth for inventory, serial tracking, and accounting wherever its architecture supports those responsibilities.

#### Order integration

A website order must create or synchronize a proper sales/order record in the ERP without creating duplicate transactions.

Use a transaction-safe integration strategy appropriate to the existing architecture.

Requirements include:

- Unique external order references.
- Idempotent order processing.
- Server-side input validation.
- Reliable retry handling.
- Error logging and reconciliation.
- Consistent customer and order references.
- Correct payment and fulfillment statuses.
- Controlled access to administrative APIs.
- Protection against duplicate submissions.
- Auditable stock changes.

Do not allow a public customer request to directly manipulate ERP stock or financial ledgers.

#### Inventory consistency

Inspect how the current ERP tracks inventory, including branch and warehouse stock.

Implement reservation, deduction, or adjustment behavior consistent with the current business rules.

Prevent overselling when multiple customers attempt to order the same available stock.

Do not deduct inventory twice when an order is retried, synchronized, canceled, or returned.

Define when stock is reserved, when it is committed to a sale, and when it is released after cancellation.

#### Serial-number-controlled products

For laptops and other serialized electronics, preserve the existing serial-number controls.

Do not assign the same physical serial number to two completed sales.

Use the existing ERP sales and serial allocation logic instead of bypassing it.

#### Financial integrity

COD orders must not appear as received cash until collection is recorded.

Preserve existing invoice numbering, ledger rules, sales reporting, EMI records, and accounting integrity.

If the current architecture requires an intermediate order state before generating a finalized sales invoice, follow that design.

### 13. PERFORMANCE AND MOBILE-FIRST OPTIMIZATION

The current site has been reported to load slowly and sometimes display content late during scrolling. Diagnose these issues instead of merely adding a loading animation.

Inspect:

- Initial server response.
- Client-side JavaScript execution.
- Rendering and hydration.
- API and database query duration.
- Unnecessary network requests.
- Image dimensions and compression.
- Font loading.
- Large component trees.
- Product-list rendering.
- Dashboard table performance.
- Repeated state updates and rerenders.
- Cache configuration.
- Third-party scripts.
- Memory usage and console errors.

Use the existing framework's compatible performance features.

Where appropriate:

- Prefer server rendering for indexable content.
- Use static generation or caching for suitable public pages.
- Revalidate public product data when ERP changes occur.
- Keep inventory and checkout validation authoritative and fresh.
- Paginate large datasets.
- Use virtualization for genuinely large administrative tables.
- Lazy-load below-the-fold content.
- Prioritize the main product image.
- Avoid blocking the initial page render on noncritical content.

Measure Core Web Vitals and set these proposed targets:

- LCP: 2.5 seconds or less.
- INP: 200 milliseconds or less.
- CLS: 0.1 or less.

These are target thresholds, not assumed current results. Validate with laboratory tests and real-user data when available.

Do not introduce stale prices or stock information simply to improve caching scores.
